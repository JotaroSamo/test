## 🔬 Виды тестов — объяснение простыми словами

### 1. Юнит-тесты (Unit Tests)
**Папка:** `Tests/Unit/`
**Атрибут:** `[Category("unit")]`

> Представь что у тебя есть калькулятор. Юнит-тест проверяет **один конкретный метод**:
> "2 + 2 = 4?" — и всё. Никакого браузера, никакой сети — только логика.

**Когда использовать:** когда пишешь вспомогательные классы, валидаторы, утилиты.

**Характеристики:**
- ⚡ Самые **быстрые** (миллисекунды)
- 🔒 **Изолированные** — не зависят ни от чего внешнего
- 🎯 Проверяют **одну функцию** за раз
- 📐 Паттерн: **Arrange → Act → Assert** (подготовь → действуй → проверь)

```
Пример: PasswordValidator.IsValid("Password123") должен вернуть true
```

---

### 2. Смоук-тесты (Smoke Tests)
**Папка:** `Tests/Smoke/`
**Атрибут:** `[Category("smoke")]`

> Представь что ты включил телевизор и просто проверяешь — он вообще включился?
> Экран есть? Звук есть? Смоук-тест — это "не горит ли что-нибудь?"

**Когда использовать:** сразу после деплоя, каждые 30 минут в продакшене.

**Характеристики:**
- 💨 **Быстрые** (до 30 секунд на весь набор)
- 🚨 Запускаются **первыми** — если упали, остальные не запускаем
- ✅ Только **критические** проверки: открылась страница / форма видна / сервер отвечает
- ❌ Не проверяют детали — только "живой или нет"

```
Пример: страница логина открывается и форма видна → OK
```

---

### 3. Интеграционные тесты (Integration Tests)
**Папка:** `Tests/Integration/`
**Атрибут:** `[Category("integration")]`

> Представь что ты хочешь проверить телефон не открывая его: позвонил — трубка взяла?
> Интеграционный тест проверяет **реальное взаимодействие компонентов через HTTP**,
> но без браузера — напрямую как сервер разговаривает с клиентом.

**Когда использовать:** для проверки API, HTTP-ответов, доступности сервисов.

**Характеристики:**
- 🌐 Ходят по **реальной сети** (отличие от юнит-тестов)
- 🚫 **Без браузера** (быстрее чем E2E)
- 🔍 Проверяют **HTTP статусы**, время ответа, содержимое HTML
- ⚠️ Зависят от **доступности сервера** (могут падать если сайт недоступен)

```
Пример: GET /login → HTTP 200, Content-Type: text/html, время < 3 сек
```

---

### 4. Функциональные тесты (Functional / E2E Tests)
**Папка:** `Tests/Functional/`
**Атрибут:** `[Category("functional")]`

> Это как посадить живого человека за компьютер и дать ему задание:
> "Зайди на сайт, введи логин и пароль, убедись что попал в личный кабинет."
> Playwright управляет реальным браузером — кликает, вводит текст, читает страницу.

**Когда использовать:** для проверки пользовательских сценариев от начала до конца.

**Характеристики:**
- 🎭 Используют **реальный браузер** (Playwright + Chromium)
- 🐢 **Медленнее** всех (секунды на тест)
- 📖 Проверяют **бизнес-сценарии**: войти → увидеть → выйти
- 🏗️ Ломаются при изменении **UI** (поменяли id кнопки → тест упал)

```
Пример: student/Password123 → нажать Submit → увидеть "Logged In Successfully"
```

---

### 5. Нагрузочные / Стресс-тесты (Performance / Load / Stress Tests)
**Папка:** `Tests/Performance/`
**Атрибут:** `[Category("performance")]`

> Представь что ты открыл магазин и хочешь знать: что будет если придут 1000 покупателей?
> Нагрузочный тест отправляет много одновременных запросов и смотрит — держит ли сервер.

**Когда использовать:** перед большим релизом, после оптимизации, по расписанию.

**Виды:**
| Тип | Что проверяет | Как |
|-----|---------------|-----|
| **Performance** | Время ответа одного запроса | 1 запрос → измерить мс |
| **Load** | Поведение под нормальной нагрузкой | 10 одновременных запросов |
| **Stress** | Точка отказа при превышении нормы | 1→5→15→25 пользователей |
| **Stability** | Нет деградации со временем | 30 запросов подряд → сравнить среднее |

**Характеристики:**
- 🏋️ **Медленные** (минуты)
- ❌ **НЕ запускаются** при каждом push (дорого и долго)
- ⏰ Запускаются **по расписанию** (в 6 утра по будням) или вручную

## ▶️ Как запускать тесты локально

```bash
# Все тесты сразу
cd Tests
dotnet test

# Только определённый вид (подставь нужную категорию)
dotnet test --filter "Category=unit"
dotnet test --filter "Category=smoke"
dotnet test --filter "Category=integration"
dotnet test --filter "Category=functional"
dotnet test --filter "Category=performance"
```

**Перед первым запуском** — установи браузер для Playwright:
```bash
cd Tests
dotnet build
pwsh bin/Debug/net10.0/playwright.ps1 install chromium
```

## 🔄 CI/CD — что это и зачем

**CI (Continuous Integration)** = "каждый раз когда ты пушишь код — тесты запускаются сами".
Ты не забудешь запустить тесты, и сломанный код не попадёт в main.

**CD (Continuous Deployment)** = "после успешных тестов — отчёт публикуется сам".
Allure-отчёт автоматически появляется на GitHub Pages.

### Как выглядит пайплайн

```
Каждый push в main:
                                          ┌──────────────────┐
   ┌─────────────┐   ┌─────────────┐     │  functional-tests │
   │  unit-tests │   │ smoke-tests │──┬──┤  (ждёт smoke +   │──┐
   │  (~30 сек)  │   │  (~1 мин)   │  │  │   integration)   │  │
   └──────┬──────┘   └─────────────┘  │  └──────────────────┘  │
          │                           │                          │
          │  ┌────────────────────┐   │                          ▼
          └──┤ integration-tests  │───┘              ┌─────────────────────┐
             │    (~30 сек)       │                  │   allure-report     │
             └────────────────────┘                  │ (собирает всё и    │
                                                     │  деплоит на Pages) │
   По расписанию / вручную:                          └─────────────────────┘
   ┌──────────────────────┐
   │  performance-tests   │
   │      (~5 мин)        │
   └──────────────────────┘
```

### Почему такой порядок?

- **unit** и **smoke** запускаются **параллельно** — экономия времени
- **integration** ждёт **unit** — если логика сломана, нет смысла проверять API
- **functional** ждёт **smoke + integration** — если базовые проверки упали, E2E тоже упадут
- **performance** — только по расписанию, чтобы не нагружать сайт каждым push'ем

### Главное правило пирамиды тестов

```
        /\
       /E2E\          ← мало, медленно, дорого
      /──────\
     /  Integ \       ← средне
    /────────────\
   /    Unit      \   ← много, быстро, дёшево
  /────────────────\
```

Чем выше в пирамиде — тем меньше таких тестов должно быть.

## 📊 Allure-отчёт

После каждого CI-запуска автоматически публикуется отчёт.

**Как читать:**
- **Suites** — группировка по папкам (Unit Tests, Smoke Tests, и т.д.)
- **Features** — группировка по функционалу (Login Feature, Password Validation)
- **Stories** — конкретные сценарии внутри фичи
- **Steps** — шаги внутри теста (видно что именно происходило)
- 🟢 **passed** — тест прошёл
- 🔴 **failed** — тест упал (кликни → увидишь шаг где упало и сообщение об ошибке)
- 🟡 **broken** — тест упал из-за ошибки в коде теста (не в приложении)

## ❓ Частые вопросы

**Q: Тест упал в CI, но локально проходит — почему?**
A: Скорее всего проблема с окружением. Проверь: версия .NET, установлен ли браузер, доступна ли сеть.

**Q: Когда писать юнит-тест, а когда функциональный?**
A: Если тестируешь **логику** (алгоритм, расчёт, валидацию) → юнит.
Если тестируешь **сценарий пользователя** (зашёл, нажал, увидел) → функциональный.

**Q: Почему нагрузочные тесты не запускаются при каждом push?**
A: Они отправляют десятки запросов к реальному сайту. Это нагружает сервер и занимает несколько минут. Запускаем только когда нужно.

**Q: Что значит `[Category("smoke")]` в коде?**
A: Это метка. Когда запускаем `dotnet test --filter "Category=smoke"` — выполняются только тесты с этой меткой. Так разные виды тестов можно запускать отдельно.
